**Detection floor: 36.8%** (max spread). This is **well above the plan's 5% target**.
The load-generator rewrite removed the client-side overhead (javapi plaintext went
9.8k -> ~33-38k req/s, and latencies collapsed) but the residual run-to-run spread
is OS/Windows noise: 6 physical cores with all JVMs sharing them, no CPU pinning,
and no timer/power tweaks. See the decision note at the bottom of this file.

## Decision note — detection floor exceeds 5%

Task 2 Step 6 of the hardening plan requires a run-to-run spread below 5% before
Phases 2-5 can be trusted; measured spread is 2.6-36.8%. Probable causes:

- **Windows 10 host**: default 15.6 ms timer resolution, no CPU affinity/pinning,
  background services, no isolated cores. The plan assumed a Linux runner.
- **Shared cores**: harness JVM + one server JVM on 6 physical cores.
- The CI gates run on GitHub Actions **Ubuntu**, which typically has far lower
  variance — this Windows box may just be too noisy to enforce the 5% floor locally.

Options to satisfy the checkpoint before starting Phase 2:

1. **Treat CI (Linux) as the measurement authority** and keep the Windows numbers
   directional only — re-run the baseline on a Linux runner and gate there.
2. **Median-of-N**: have the harness run each workload 3x per app and report the
   median req/s, amortizing OS noise. Costs ~3x compare runtime.
3. **CPU affinity + process priority**: pin harness to cores 0-3 and the server to
   core 4 (Windows `start /affinity`), raising priority to HIGH — best-effort, may
   not fully close a 37% spread on a busy desktop.
4. Accept the 36.8% floor and only trust improvements larger than it (weak).
